怎么用这个站

两条线索交替使用：先建骨架，再填细节。骨架来自 learning-guide（包怎么分层、一次调用怎么穿过它们），细节来自 16 章教程（每一层的真实代码与实验）。

① 用「五层路径」决定读什么

每个阶段给出包、阅读顺序、关键点和对应章节。一个阶段结束再进下一个，不要按目录顺序乱翻。

② 每读一个模块，配合对应章节

例如读 packages/agent/src/agent-loop.ts 时打开第 04 章，里面有逐行对照和可以离线跑的 faux 实验。

③ 实验优先于阅读

教程实验默认走 faux 模型：不花钱、可复现，事件流与真实 provider 同构。跑一遍比读三遍收获大。

④ 用问题驱动验证

每章末尾有自测题和课后作业。答不上来的，回到 关键文件速查 精读对应文件。

你只有 30 分钟

读第 00 章（全景 + 三层消息 + 一次请求的旅程），再把第 04 章的 agent-loop 实验跑一遍。这两件事能覆盖理解 pi 的 60%。

前置自检

来自 learning-guide/prerequisites.md 的优先级分级。下面 12 项是真正决定你读源码速度的，勾选状态会保存在本地。

必须（⭐⭐⭐）

  • JS / TS：泛型、联合类型、类型收窄、satisfies、模块解析
  • 异步：Promise、async/await、AsyncIterator 与流式消费（for await）
  • JSON Schema 与 tool calling：模型返回的 tool call 长什么样、怎么回填结果
  • Node.js：fs/promises、child_process、readline、AbortSignal

加分（⭐⭐）

  • 终端与 ANSI 转义序列（光标、颜色、光标定位）
  • WebSocket 与二进制帧、分帧协议
  • TypeBox / JSON Schema 的 schema→类型推导
  • CBOR 是什么、为什么不用 JSON
  • Monorepo：workspace 协议、包之间单向依赖
  • 状态机与事件驱动设计
  • 插件 / 扩展架构（loader + 生命周期钩子）
  • 测试：node:test、vitest、faux provider 打桩
缺项不用等

「必须」四项里缺两项，先补 TS 泛型和流式异步，这两样在 agent-loop.ts 里随处可见。其余的在读的过程中补，比先学完再读效率高。

五层学习路径

自上而下是依赖方向：上层 import 下层，反之不会发生。所以也可以反过来读——从最底层往上，读完一层就能理解下一层的输入是什么。

L1

基础协议与工具 · protocol / telemetry

1–2 天▸

这一层只回答两个问题：进程之间怎么说话（protocol），运行时怎么上报（telemetry）。代码量小，但定义了全仓库共用的消息形状。

文件看什么
packages/protocol/src/schemas.tsTypeBox 定义的消息模式；schema 即类型
packages/protocol/src/codec.tsCBOR 编解码，为什么比 JSON 更适合传二进制
packages/protocol/src/framing.ts分帧：大消息怎么切、流式怎么续
packages/telemetry/src/index.ts供应商中立接口：span 与 sensitive 标记
packages/telemetry/src/noop.ts · memory.tsNull Object 模式；用内存实现做测试替身

关键点：接口与实现分离（不绑死具体遥测库）、Null Object 让「不开启遥测」不需要到处判空、sensitive 标记决定哪些数据不出机器。

延伸：learning-guide/protocol.md 有逐节讲解。

L2

AI 抽象与 Agent 核心 · ai / agent（最核心）

3–4 天▸

整个框架的心脏。ai 把 20 多家厂商的 API 收敛成「一种消息格式 + 一种流式事件协议」；agent 则是「调用模型 → 执行工具 → 把结果喂回模型」的循环。

packages/ai 阅读顺序

  1. src/types.ts — Provider / Model / Message / Content / ToolCall
  2. src/model-catalog.ts — 模型注册表与元数据
  3. src/providers/openai.ts — 先读一个完整 Provider 实现
  4. src/providers/anthropic.ts — 对比：tool use 与流式差异
  5. src/api/openai-responses.ts — 流式响应如何被统一
  6. src/oauth.ts — 设备码流程与 token 管理
注意：providers/ 只是注册入口

providers/openai.ts 只有十几行——真正的协议适配在 src/api/*.ts。learning-guide/agent-and-ai.md 专门解释了这处容易找错文件的坑。

packages/agent 阅读顺序（⭐⭐ 最核心）

  1. src/types.ts — Tool / ToolResult / AgentState / Harness
  2. src/agent-loop.ts — 核心循环，值得花一整天
  3. src/agent.ts — 状态持有、消息历史、工具注册
  4. src/harness/ — 各类消息处理器与 tool result 格式化
  5. src/search/ — 内置搜索工具
用户输入→调 LLM→解析 tool call→执行工具→结果回填→再调 LLM↺

深读 agent-loop.ts 的方法：先通读标记疑问 → 画出状态转换 → 跟踪一次完整 tool call 请求 → 改代码看行为变化。

核心概念

六个概念串起整个框架。每个都指向「定义 → 为什么存在 → 去哪读」。

Provider（提供商）

把不同 LLM 服务的差异收敛成一个接口。它不是「一个函数」，而是「注册表 + 适配器 + 鉴权」三件套：providers/*.ts 负责注册与元数据，api/*.ts 负责真正把内部 Message 翻译成厂商协议、再把流式响应翻译回来。

为什么要这层：没有它，每加一家模型都要改 agent 循环、UI、会话存储三处。有了它，加厂商只动 ai 一个包。第 02 章

Tool（工具）

Agent 可以调用的函数：name + description + JSON Schema 入参 + 执行函数。模型不执行工具，它只返回「我要调哪个、参数是什么」；执行永远在宿主进程里。这是权限模型的基础。第 03 章 · 第 06 章

Agent Loop（智能体循环）

整个框架的心跳：调模型 → 解析工具请求 → 执行 → 结果回填 → 再调模型，直到模型不再请求工具。内核不到 1000 行，其余十几万行都在处理真实世界的边界：厂商差异、取消、重试、流式渲染、长上下文。

收集上下文→调 LLM→有 tool call?→执行并回填↺否则结束

Session（会话）

append-only 的 JSONL 树，不是线性日志。树的形状让「回退到某条消息再换个问法」变成一次分支，而不是丢掉后面所有记录。上下文快满时由 compaction 把旧消息折叠成摘要，摘要本身也是树上的一个节点。第 08 章 · 第 09 章

Extension（扩展）

pi 的设计取向是「小内核 + 大扩展」：codemode、MCP、tool search 都是内置扩展；plan mode、危险命令确认、子代理是示例扩展。加载器在启动时扫描 ~/.pi/extensions/ 与项目 .pi/extensions/。想加功能，先想想是不是该写扩展而不是改内核。第 11 章

三层消息

Message ⊂ AgentMessage ⊂ SessionEntry：发往模型的最窄，运行时的更丰富（带工具结果、事件），落盘的最全（带时间戳、父指针）。convertToLlm 就站在这条边界上，决定哪些东西进得了请求。第 00 章

常见问题

为什么用 CBOR 而不是 JSON？

CBOR 是二进制格式：更紧凑、解析更快，且原生能装二进制数据（图片、附件）不需要 base64 膨胀。对「高频、含二进制、跨进程」的消息通道，这三条都成立。

Agent 如何管理上下文窗口？

两层：先由 compaction 在接近上限时把旧消息折叠成摘要（第 09 章），再由 convertToLlm 决定哪些条目最终进入请求。摘要节点本身留在会话树里，可以被后续请求引用。

Tool calling 到底是谁在执行？

模型只输出「调用哪个工具、参数是什么」（结构化 JSON），宿主进程负责解析、校验 schema、执行、把结果作为新消息发回。所以工具的权限、超时、沙箱全都由宿主决定——这是 pi 能把危险操作交给扩展去管的前提。

扩展是怎么加载的？

启动时扫描 ~/.pi/extensions/ 和项目 .pi/extensions/，动态加载模块，注册工具 / 提供商 / 命令 / 主题，并挂到生命周期钩子上。细节见第 11 章与 docs/extensions.md。

TUI 的差分渲染是什么？

对比新旧两棵渲染树，只把变化的单元格写到终端。终端重绘昂贵且会引起闪烁，全屏重绘在滚动历史里几乎不可用——所以差分不是优化，是必需品。见第 12 章。

providers/openai.ts 只有十几行，是不是我看错了文件？

没看错。providers/ 是注册与元数据入口，真正的协议实现（请求体翻译、流式事件解析）在 packages/ai/src/api/。learning-guide/agent-and-ai.md 专门讲了这处分层。

教程版本和仓库版本对不上怎么办？

教程基于 pi-coding-agent 1.5.2 的发布包（从 sourcemap 还原），仓库是 0.0.3 的开发版本。行号会有偏移，但结构基本一致。以教程的图理解机制，以仓库的代码做实验。

动手实践

四个由易到难的练习，每个都有明确的「完成标准」。做完这四个，你就能说「我读过 pi」而不是「我翻过 pi」。

① 加一个工具

写一个 wordcount 工具（schema + handler），注册到 coding-agent，让模型在对话里调用它。

完成标准：模型主动调用、拿到结果、用结果回答问题。第 06 章

② 写一个扩展

基于 examples/extensions/ 写一个：拦截 bash 里的特定命令并要求确认。

完成标准：命令被拦下时能看到你的提示。第 11 章

③ 观察一次压缩

把上下文窗口调小，跑一段长对话，打印压缩前后的消息数量与 token 数。

完成标准：能画出压缩发生在哪一步、摘要长什么样。第 09 章

④ 组装 mini-pi

不抄 agent 源码，只用 ai + 自己写的循环，做出能读文件、跑命令的最小 agent。

完成标准：几百行、能完成「找到并修复一个小 bug」。第 15 章

学习建议（原文精神）

先类型后实现：每个包的 types.ts 是理解该包的钥匙。重点攻 agent-loop.ts。对比不同 provider 的实现。不要只读代码——改测试、跑实验、改代码看行为。
